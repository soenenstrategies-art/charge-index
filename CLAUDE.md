# Charge Index™ — Soenen Strategies

Client project for Jen Soenen (Soenen Strategies, a time-management coaching business). Built by Josh as a paid engagement, on infrastructure registered to Jen from day one — see "Account ownership" below before touching any external service.

Full product spec, data model, algorithms, and phased build plan: **`Planning/Build Plan.md`**, which lives *outside* this repository — it's business planning material, not app source. Read it for anything beyond "how do I run this app."

**It may not be beside you.** During the build it sat one level up (`../Planning/`), which is why references below are written that way. In a fresh clone there's no parent folder to read: Jen's copy is in the "For Jen — Charge Index" folder she was given at handover, under `Planning notes/`. If you can't find it, say so rather than guessing at the reasoning behind a design decision — this file records the decisions themselves, which is usually enough.

`README.md` is the public-facing overview. **`HANDOFF.md` is the runbook for handing the project to Jen — keep it current** when accounts, keys, switched-off features or deploy steps change.

## Stack

Next.js 16 (App Router, Turbopack) + React 19 + TypeScript + Tailwind v4, deployed on Vercel, backed by Supabase (Postgres + Auth), Stripe for payments (not yet wired). Cloudflare Turnstile guards signup and login.

## Two dev servers — pick the right one

- **`./scripts/dev-local.sh`** (port 3200) — the app against a **local** Supabase stack (Docker), with Cloudflare's always-passes Turnstile test keys. Use this for anything that signs up, deletes or experiments. Emails land in the local inbox at `http://localhost:54324`; nothing leaves the machine. This is the default preview in `.claude/launch.json`, deliberately: a browser session that can create and delete accounts shouldn't be pointed at Jen's live database.
- **`npm run dev`** (port 3000) — reads `.env.local`, so it talks to the **real hosted database**. Fine for looking at real data; wrong for anything that writes.

Phase 4 (daily check-in grid), built 2026-09-14 to Jen's prototype and mockups 03–06:

- **`/track/[sessionId]`** — `page.tsx` loads the session, its entries and notes under RLS and hands them to `check-in.tsx`: five tiles per hour, keyword chips for the level just tapped, day tabs, streak dots, the three daily reflections, Back / Next day. The header rail uses the prototype's `day_count + 2` segments.
- **Writes go straight from the browser to Supabase**, relying on the RLS policies from Phase 1 — no API route in between. `src/hooks/useSaveQueue.ts` serialises writes per key and collapses anything queued to the newest value, so rapid taps on one hour can't land out of order. Failed writes stay visible with a Retry and are re-sent on the browser's `online` event. Reflections save on a 700ms debounce, and flush early on day change, blur, and tab hide.
- **Tapping the selected tile again clears the hour** and deletes the row. This is a deliberate addition — the prototype had no undo, so a mis-tap would have been recorded as real data rather than a skip.
- **The log reopens on the furthest day with anything logged** (`resumeDay()` in `src/lib/progress.ts`), or the next day if that one is full. Not derived from `start_date`, because that needs the client's timezone, which isn't stored anywhere yet.
- **"See my results"** calls the `completeSession` Server Action, which sets `status = 'completed'` and redirects to `/track/[sessionId]/complete`. It's an action rather than a side effect of visiting `/complete` because Next.js prefetches links — a mutating GET could complete a session nobody finished. The completion screen shows session facts only (session, days, hours logged, waking window). Jen's mockup also shows the client their peak window and two upsell cards; that's held back pending a product decision, since it conflicts with "the client never sees analysis."
- **`start_date` now comes from the browser's local date**, stamped at submit in `setup-form.tsx` and accepted within ±1.5 days of server time. Postgres `current_date` is UTC, so an evening setup in Toronto used to start on tomorrow's date.
- **`FieldLabel` requires `htmlFor`.** No form label in the app was linked to its field; TypeScript now enforces it.

**Corporate teams (2026-09-30).** Built in four stages against `../Planning/Corporate Build Plan.md`; every decision in that file was Josh's or Jen's.

- **Shape:** `companies` → `teams` → `team_rounds` (one tracking cycle) → `team_plans` (one per released round). Membership is `team_memberships` (`lead` | `member`); `tracking_sessions.round_id` ties a week to a round. Migrations `20260930120000`, `20260930140000`, `20260930160000`.
- **How a team starts:** Jen creates the company and team, which also mints two invites. The **lead link is single use** — first person to open it becomes the lead. **Seats are the payment gate**: 0 until she sets them, and `join_team()` refuses the member link until then, then caps it at the seat count. No Stripe involved.
- **The privacy boundary is the point.** A lead sees who joined and how far along they are — never an entry, a curve or a result. That can't be expressed in row-level security alone, because counting progress means reading rows the lead may not, so **`team_progress(team)`** runs as owner, checks the caller is that team's lead or a coach, and returns aggregates only. Same for the plan: it's computed at release by Jen (who can read everything) and **stored**, so the lead reads a result, and a released plan can't drift when someone edits an hour later.
- **Policies on `teams` / `team_memberships` must not read each other** — that's mutual recursion (42P17). Use the security-definer helpers `is_team_member()` / `is_team_lead()`.
- **Three time functions, deliberately separate:** `entry_window_open` (pure clock), `entry_window_closed` (past its 24 hours — what "missed" means), and `entry_hour_open` (the permission: coach OR open). Using the permission one for progress makes every hour look fine for a coach.
- **The plan's thresholds are starting points, not findings:** `TEAM_MAJORITY` 0.6, `SPLIT_GAP_HOURS` 3, `MAX_MEETING_HOURS` 4, and members under `MIN_HOURS_FOR_RESULT` are excluded and named. Jen will move these.
- **Seeding gotcha:** `daily_entries.energy_pct` only accepts 10/25/50/75/100. A seed script with 80s in it silently inserts nothing if it doesn't check errors.

**Jen's review with Josh, round two (2026-09-29).** They went through the whole product together. What changed:

- **Removed:** AI insight drafts everywhere (table, lib, panel, `@anthropic-ai/sdk`, the `ANTHROPIC_API_KEY` dependency — **no Anthropic account is needed at all now**), `/coach/sessions` and its nav tab, and the curve on the client's results screen. ## Security

**Privilege escalation, found and fixed 2026-09-14** (`supabase/migrations/20260914203306_restrict_profile_updates.sql`). Supabase grants `anon` and `authenticated` write access to every column, leaving RLS as the only gate, and Phase 1's `profiles_update_own` didn't restrict columns. So any signed-up client could `update profiles set role = 'coach'` on their own row — which opened every client's sessions, entries, notes and profiles, plus the coach-only tables — and could set their own `stripe_customer_id`. Proven live with test users before the fix (a test client promoted itself and read another client's "For Jen" note). No real accounts existed, so no data was exposed. Fix: column-level privileges — clients may update `profiles.full_name` and nothing else. Phase 1's verification had tested clients reading each other but never a client changing their own role.

**Bot check on signup and login (Cloudflare Turnstile, 2026-10-06).** `src/components/auth/Turnstile.tsx` renders the widget and puts its token in a hidden `captcha_token` field; `captcha()` in `src/app/auth/actions.ts` passes it to Supabase as `options.captchaToken`. Two things worth knowing:

- **It sits on both forms, not just signup.** Once a project has a CAPTCHA enabled, GoTrue demands a token on *every* auth call — login and password recovery included. A signup-only build would lock existing clients out at the login page.
- **Switched on 2026-10-07** with Jen's own Cloudflare widget, verified end to end: the live signup page served the widget container and hidden `captcha_token` field, the box rendered in a browser, and a real sign-in through it succeeded. **A consequence worth knowing: preview deployments can no longer sign in** — their one-off `*.vercel.app` addresses aren't in the widget's hostname list and the site key isn't set for Preview, so they can't produce the token GoTrue now demands. Add the preview hostname to the widget if a preview login is ever needed. A new site key also does nothing until a redeploy, since `NEXT_PUBLIC_*` is inlined at build time.
- **It switches on with two keys, no code change.** The widget renders only when `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is set, and with no key the forms are byte-for-byte what they were (verified: no widget, no hidden field, no request to Cloudflare, signup still works). The site key goes in Vercel; the matching secret goes in the hosted project's **Auth → Attack Protection** settings. Both must be set together — a secret with no site key locks everyone out, a site key with no secret lets bots through.
- Supabase's own wording for a missing token is `captcha protection: request disallowed`. `authMessage()` rewrites anything matching `/captcha/i` into "The bot check didn't go through. Tick it again, or refresh the page."
- Locally it is **enabled** in `supabase/config.toml` with Cloudflare's documented always-passes test secret, so the local stack behaves like production. `dev-local.sh` supplies the matching test site key.
